# 验证准则

改动只有拿得出证据才算完成：它被真实运行过，并且结果符合预期。交付时写明跑了什么、看到了什么，让人审证据，而不必逐行读 diff。

## 验证就是把改动跑起来

- 端到端跑一遍比测试通过更重要。单元测试全绿，功能照样可能是坏的。
- 按改动类型选运行方式：Web 用 Claude Chrome 扩展，移动端用 iOS / Android MCP，桌面应用用 computer use，后端在本地把服务跑起来。
- 提交前先跑 `verify` skill。它放在 `.claude/skills/` 下，可以有多个，用离被改代码最近的那个。
- 仓库里还没有 `verify` skill 时，先弄清怎么启动应用并完成这次验证，再建议把步骤沉淀成 skill。它是冒烟测试的基座，要经得起反复迭代和压力测试，做到又快又稳。
- 开 PR 前在本地跑完测试、构建和 linter。没在本地测就推上去，是拿共享的 CI 和 review 时间去抓自己本可以抓到的 bug。

## 检查失败时

- 检查失败就去修代码，再跑一遍。修了三轮仍然失败就停下来找人，并说明是哪项检查、试过什么、为什么需要人看，不要让人自己从 diff 里推断。
- 遇到不稳定（flaky）的测试，不要跳过、加 sleep 或重试到通过。去找根因；找不到就删掉这个测试，并写下原因。
- 不要修改用来评判当前改动的规则，例如 `REVIEW.md` 和门禁配置。改动能改掉评判自己的检查，这个检查就失效了。规则确实该改时，单独提一个改动，交给代码所有者。
- review 结论只对被审的那个 commit 有效。review 进行中不要继续 push；有了新 commit，旧的通过结论就作废。

## 写什么测试

缺少能验证这次改动的测试时，先把测试补上：生成测试、基准和规格的成本很低，生成后可以反复运行，几乎不再消耗 token。下面三种最值得投入，只能选一种时选端到端测试。

### 端到端测试（E2E）

描述真实的用户流程，例如加入购物车、结账、到达确认页。它很难被糊弄：功能要么整个可用，要么不可用，完成标准明确。

- 失败时要能指出坏在哪一步，并附上截图和 trace，而不是只有一句 `Timeout after 30s`。
- 让自己能直接操作和观察真实运行的系统：通过 CDP、模拟器或 API harness 启动、驱动并检查应用。
- 仓库里有 feature map（从用户视角列出功能、路径、快捷键、选择器和预期结果）时，把它当作指引和评分标准。

### 属性测试（property test）

先写下一条你认为不可能被打破的陈述，再用库生成成千上万个输入去反驳它：JS/TS 用 fast-check，Python 用 Hypothesis，Rust 用 proptest。它覆盖的是人容易漏、agent 也常出错的边界情况，而且这些输入不带写代码者的偏见。

- 往返（round-trip）：编码后再解码得到原值，解析和序列化同理。
- 不变量：必须恒成立的条件，例如账户余额不能为负。
- 幂等：同一操作（迁移、规范化、重试）做两次和做一次效果相同。
- 等价：优化后的实现和朴素但正确的实现结果一致。

重写旧代码时，如果规格已经和线上行为脱节、不能再作为验证依据，属性测试尤其有用。

### 差分测试（differential test）

用于行为应当保持不变的大规模迁移，把旧系统当作标准答案：同样的输入分别跑旧系统和新系统，结果不同就是 bug 或破坏性变更。

- 输入用随机生成的数据或线上流量的采样。
- 比较前先归一化无关差异，例如空白字符。
- 新旧系统本该不同的地方，记在一份“已批准差异”清单里。

### 测试本身的质量

- 测试要稳。不稳定的测试会让你养成“再跑一次”的习惯，而不是去修出问题的代码。
- 测试要快。测试慢，跑的次数就少，每次攒下一大批改动，出了问题难以定位。
- 重的测试放到提交之前跑。

## Review 与多轮验证

- 每一轮 review 或验证都接着前几轮的上下文和以往的失败来做，不要每次从头全查一遍。这样更省，发现的问题也更多。
- 只用一个 reviewer，用 `REVIEW.md` 告诉它这部分代码该关注什么。reviewer 不够好就去调它，不要在上面再叠一个更贵的 reviewer。
- 仓库有可靠性检查清单时，先读 diff，只检查触发条件命中的条目（通常 3 到 10 条），不必整份过一遍。例如“`--resume` 会加载旧 transcript”这一条：session 存储或消息类型有变动时，确认新增字段在旧 transcript 里不存在的情况下也能安全加载。
- 给发现的问题标注重要性：Important（该修）、Nit（小问题）、Pre-existing（改动之前就存在的 bug，不算在这次的作者头上）。

## 提交记录

- 每个 commit 都注明它是怎么验证的，这样事后能查出哪些提交没验证过。例如在 commit message 末尾加一行 `Verified: e2e (verify skill)`；没验证就写 `Verified: none` 并附原因。
- 被提交门禁拦下时（会话里没跑过 `/code-review` 或 `/verify`），去补做验证。确实没法验证的，在 commit message 里说明原因。

## 搭建和维护验证体系时

以下适用于新增或调整检查、门禁和 review 规则的任务。

- 检查由代码所有者来写，并打磨到“所有者会指出的问题，它也会指出”为止。
- 可靠性清单的每一条都包含三样东西：能从 diff 读出的触发条件、要做的检查、背后的事故或 PR。
- 评判规则放在被评判的改动碰不到的地方：`REVIEW.md` 从 base 分支或默认分支读取，不从 PR 的改动里读。
- 便宜的检查先跑。可以用 hook 在 Claude 结束时自动跑测试，或用 `/goal` 把“测试全部通过”设为目标。
- 新门禁按 off、observe、enforce 三档上线。observe 只记录“本来会拦下什么”，用来排查误报、确认不会误伤任何人，之后再切到 enforce 真正拦截。
- 门禁要留出口：允许在 commit message 里说明为什么没验证；同一会话已经被拦两次，第三次放行，免得卡死。
- 同一类问题反复出现时，加一个 hook，或在 CLAUDE.md 里写一条更明确的规则。

### 考核 reviewer 本身

- 持续跟踪三组数据：合并后被 revert 的改动、合并前被维护者打回的改动，以及一组规模相当、一直没出问题的改动（作对照）。
- 正式评估用历史事故和 revert 来做：把仓库还原到当时 review 的状态，每个样例配一句话的答案说明 bug 是什么，只有准确描述出这个 bug 的发现才得分。
- 用已合并且稳定的改动作对照，防止过度报告。调参用的数据集和固定的测试集分开。
- 分别衡量原始发现、验证后、最终 review 三个阶段的召回率，才能看出系统有没有把已经找到的 bug 弄丢。只看一个端到端总分看不出这一点。
- 除了“对不对”，还要评“值不值得改”：是必须修、应该修，还是小问题。
- 召回率调到“再往上就是在过拟合评估集”为止。

### 把漏掉的问题变成规则

- 从人工 review 评论和被 revert 的 PR 里提炼模式。至少在两个 PR 里出现、并且能从 diff 识别出来，才算候选规则。让三个 agent 尝试证伪，最后由人在 PR 里审批。
- 对关联了已知事故的 PR 重放三个 bug finder。至少两个能找到，说明这个 bug 可以被检测到；如果是在一个小 diff 上被漏掉的，这就是值得写进 `REVIEW.md` 的缺口。
- 规则也要清理。测试集、验证步骤和 .md 文件放着不管只会越来越长，要定期精简。
